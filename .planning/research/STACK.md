## Database Decision: Postgres > SQLite (for *this* project)

This is the single decision worth more than one paragraph. **Recommendation: Postgres 17 in the compose file.** Confidence: HIGH.

| Criterion | SQLite | Postgres | Verdict |
|-----------|--------|----------|---------|
| Single-user fit | Built for it | Overkill in theory | SQLite wins on paper |
| ACID for money | Yes | Yes | Tie |
| Decimal/numeric arithmetic | `REAL`/`NUMERIC` is stored as text — fine, but no native arithmetic precision guarantees | First-class `NUMERIC(20,4)` with exact arithmetic in SQL | **Postgres** — money rollups happen in SQL aggregations |
| Concurrent read while writing | WAL mode allows it, but writers serialize globally | MVCC, no global writer lock | **Postgres** — poller + UI both happily writing/reading |
| Joins against FX rate table | Fine for small data | Fine, with proper plans | Tie |
| Backup story | `sqlite3 .backup` file copy — trivial | `pg_dump | gzip` — also trivial | Tie (both 1-line cron) |
| Migrations | Alembic supports both, but SQLite ALTER TABLE is anemic — most schema changes require batch operations / table rebuilds | Full ALTER TABLE, types, constraints | **Postgres** — finance schemas evolve a lot |
| Compose footprint | Zero | One container, ~80 MB RAM idle | SQLite wins on resource use |
| LLM categorizer extension | `pgvector` exists for Postgres, no equivalent for SQLite | Drop-in `pgvector` extension | **Postgres** — keeps the LLM door open |
| Future "I want to query from another tool" | File lock contention | Connection-based | **Postgres** |

**Why this beats the obvious "SQLite wins for one user":** the project explicitly has *two concurrent writers* (the APScheduler poller and the user editing through the UI) and an explicit "LLM categorizer pluggable later" door, which `pgvector` opens cleanly. The cost of running Postgres in compose on a Pi-class box is ~80 MB RAM and zero ops work. There is no scenario where you regret this choice in 12 months; there are several where you regret SQLite (batch ALTER on a transactions table, vector search bolt-on, parallel poll + UI write contention).

**If you really want to run on a 512 MB device:** drop to SQLite + WAL with `journal_mode=WAL, synchronous=NORMAL, busy_timeout=5000`. Use Alembic in `--render-as-batch` mode. Don't bother with `pgvector`'s alternatives in SQLite (`sqlite-vec`) until v1.5.

**Why not DuckDB:** DuckDB is an OLAP engine, not an OLTP one. Excellent for ad-hoc analytics over your txn history; bad for the live writer (concurrent-writer story is weaker than SQLite). Optional later: export Postgres → Parquet → DuckDB for chart-heavy explorations.

## Money / Decimal Handling

**Recommendation:** A small in-house `Money` class wrapping `decimal.Decimal` + ISO-4217 currency code. **Do not** depend on `py-moneyed` (last release Nov 2022, two pyproject churn cycles old), and do not store money as floats.

```python
# domain/money.py
from dataclasses import dataclass
from decimal import Decimal, ROUND_HALF_EVEN

@dataclass(frozen=True, slots=True)
class Money:
    amount: Decimal       # always Decimal; never float
    currency: str         # ISO-4217 ('UAH', 'USD', 'EUR')

    def __post_init__(self) -> None:
        if not isinstance(self.amount, Decimal):
            raise TypeError("amount must be Decimal")
        if self.currency not in {"UAH", "USD", "EUR"}:
            raise ValueError(f"unsupported currency: {self.currency}")

    def quantize(self, places: int = 2) -> "Money":
        q = Decimal(10) ** -places
        return Money(self.amount.quantize(q, ROUND_HALF_EVEN), self.currency)
```

**Storage rules:**
- `transactions.amount` — `NUMERIC(20, 4)` not null
- `transactions.currency` — `CHAR(3)` not null
- Mono returns minor-unit integers (kopecks/cents). Convert at the edge: `Decimal(minor) / Decimal(100)` (or `1000` for some currencies — UAH/USD/EUR are all 2-place).
- All UAH-rollup math in SQL using `NUMERIC` ops; `transactions JOIN fx_rates ON tx.date = fx.date AND tx.currency = fx.currency`.
- Never `float()` a `Decimal` on the way out except for the final JSON serialization, and even then prefer string transport (`Decimal -> str`) so the JS side doesn't reintroduce float drift. The `tan-stack/react-query` hook can `Number()` only at the chart boundary.

**Why not `py-moneyed`:** abandoned-ish, brings Babel-style locale stuff you don't need, and forces the import edge to convert into its `Money` type which doesn't round-trip nicely through Pydantic. A 30-line dataclass beats it.

**Why not "minor units everywhere":** works, but every UI render and every multi-currency rollup needs an extra divide; readability cost is real over hundreds of touch points.

Confidence: HIGH.

## FX Rate Source: NBU

**Endpoint:** `https://bank.gov.ua/NBUStatService/v1/statdirectory/exchangenew?json&date=YYYYMMDD` (per-day rates, returns all currencies).
*Verified 2026-05-10 via search; the `exchangenew` path is the current one and supports `valcode=USD&date=20260510` filtering.*

**Fetch strategy:**
1. APScheduler job `fx_daily_pull` runs once per day at 12:30 Kyiv time (NBU publishes around noon).
2. Hits `?json&date=<today>` once. Parse the JSON list.
3. Upsert into `fx_rate(date PRIMARY KEY, usd NUMERIC(12,6), eur NUMERIC(12,6))` — only the currencies you hold.
4. On import: when computing UAH rollup for a transaction with `currency != 'UAH'`, look up `fx_rate.date = txn.date`. If missing (weekend, holiday, NBU late), fall back to the most recent prior `fx_rate` row (`SELECT ... WHERE date <= :txn_date ORDER BY date DESC LIMIT 1`). NBU's last-published rate stays valid until the next publication.
5. Backfill: on first run, fetch 90 days of rates (90 calls — well under any soft rate limit; NBU is generous).

**Why NBU and not openexchangerates / fixer / ECB:** the Project explicitly says NBU is authoritative for UAH conversion. Anything else introduces tax/accounting ambiguity ("which rate did you use?") for no upside. ECB doesn't publish a UAH cross-rate. Confidence: HIGH.

## Mono Polling Strategy (1 req / 60 s constraint)

**Verified facts:**
- `/personal/statement/{account}/{from}/{to}` — **1 call per 60 s per token**.
- Maximum window per call: **31 days + 1 hour (2,682,000 s)**.
- `/personal/client-info` — same 60s cooldown applies; calling either resets the timer for both.

*Sources cross-checked via the open-API documentation mirror (siomochkin/monobank-open-api-documentation) and confirmed in multiple client libraries' READMEs.*

**Recommendation:** APScheduler `AsyncIOScheduler`, in-process, single job per account.

```python
scheduler.add_job(
    poll_account,
    trigger=IntervalTrigger(seconds=65),   # 5s safety margin
    args=[account_id],
    id=f"mono-poll-{account_id}",
    max_instances=1,                       # never overlap
    coalesce=True,                         # collapse missed runs
    misfire_grace_time=120,
)
```

**Why APScheduler over Celery / Arq / Dramatiq / cron:**
- Celery + Redis broker: enormous overkill — 2 extra containers, broker ops, serialization, etc. — for 1 task every 65 s.
- Arq: Redis-based; same overhead.
- Dramatiq: ditto.
- systemd timer / host cron calling a CLI: works, but you lose shared state (last-fetched cursor, in-memory backoff) and your "single docker compose up" story now requires host-side cron files.
- Plain `asyncio.create_task` in a loop: works, but you lose APScheduler's misfire/coalesce semantics for free, which matter when the NAS sleeps or restarts.

**Backfill:** separate one-shot job that walks 31-day windows backwards, sleeping 65s between calls. A 2-year backfill = ~24 calls = ~26 minutes; runnable at first launch, then never again.

**Webhook door (deferred):** when v1.5 puts this behind a Tailscale Funnel or Cloudflare Tunnel, swap the poller for a `POST /webhooks/mono` route. The schema doesn't change. Confidence: HIGH.

## Frontend Decision

### Why React + Vite (not SvelteKit, not HTMX)

| Option | Verdict | Reasoning |
|--------|---------|-----------|
| **React 19 + Vite + TS** ✅ | Pick | Largest pool of charts, components, hooks, AI assistance. The user already prefers JS — the gain from Svelte/Vue isn't worth the smaller chart/component ecosystem. |
| SvelteKit 2 + Svelte 5 | Reasonable alt | Smaller bundle, runes are nice, but Recharts-equivalent (LayerChart) is less mature, and the user-prefers-JS constraint already accepts framework overhead. |
| Vue 3 | Fine but worse fit | Smaller English-language solo-dev community than React; no objective edge here. |
| **HTMX + Jinja** | Skip for this project | HTMX is genuinely good for forms-and-CRUD, but the Spending Dashboard is interactive (filter, drill-down by category, time range, comparison vs prior month). Building that with HTMX means lots of partial templates and `hx-get` handlers; the JS state model wins for this UX. The user explicitly prefers JS — only override if HTMX gave a 2-week delivery edge, and for this UX it doesn't. |

Confidence: HIGH.

### Why TanStack Query + nothing else

The state model:
- **Server state** (transactions list, accounts, categories, FX rates) → TanStack Query 5. Caching, revalidation, mutations, optimistic updates.
- **URL state** (current filter, selected month) → React Router 7's loaders/`useSearchParams`.
- **Truly local UI state** (modal open, form input) → `useState`.

Zustand / Redux are not needed for v1 — there is no shared client-side state of meaningful complexity. Re-evaluate only when you add a multi-step transaction split modal or cross-page selection, neither of which is in scope. Confidence: HIGH.

### Why Recharts (not Chart.js / ECharts / uPlot / Plotly)

| Library | Verdict | Why |
|---------|---------|-----|
| **Recharts 3** ✅ | Pick | Declarative React API matches the rest of the codebase; defaults look fine; ~50 KB gz; easy responsive containers; pie/bar/line/area covers every chart in the dashboard. |
| ECharts 6 | Overkill | Most powerful, ugliest defaults, biggest bundle (~900 KB), tons of imperative config. Right for enterprise BI, wrong for a personal dashboard. |
| Chart.js 4 | Reasonable alt | Smaller than ECharts, but imperative + canvas-only. React wrapper is community-maintained. |
| Plotly | Skip | Heavyweight scientific charts. |
| uPlot | Skip | Best-in-class for huge time series; you have at most a few thousand transactions a month — uPlot's value (10× faster on 1M points) doesn't apply. |

Confidence: HIGH.

### Why Tailwind 4 + shadcn/ui

- Tailwind 4 ships its own Vite plugin (`@tailwindcss/vite`) and replaces the JS config with CSS-native `@theme {}` blocks. Less to configure than v3.
- shadcn/ui is **not a dependency** — `npx shadcn@latest add button dialog input ...` copies Radix-based components into `src/components/ui/` that you own and can mutate. This avoids the lock-in problem with Mantine / Park UI / Chakra: when the vendor pivots, you don't have to rewrite. shadcn explicitly supports Tailwind v4 + React 19 since CLI v3.
- Mantine is a fine alternative if you want everything pre-built, but you trade ownership for upgrade pain and ~150 KB of CSS-in-JS runtime.

Confidence: HIGH.

## API Style: Plain REST + OpenAPI

**Recommendation:** REST endpoints emitted by FastAPI (`@app.get("/transactions")` etc.), with the OpenAPI schema piped to `openapi-typescript` to generate TS types.

```bash
# build pipeline (frontend)
pnpm openapi-typescript http://localhost:8000/openapi.json -o src/api/schema.d.ts
```

| Style | Verdict | Why |
|-------|---------|-----|
| **REST + OpenAPI** ✅ | Pick | FastAPI generates the schema for free; types flow to TS without manual DTOs; `curl` and the Swagger UI work as a debugging tool against your own NAS. |
| tRPC-like | Skip | Requires a Python equivalent of `@trpc/server` — none is mature. The "free codegen" benefit you'd be chasing is already provided by OpenAPI here. |
| GraphQL | Skip | Adds Strawberry/Ariadne, query/resolver layer, plus client cache duplication of TanStack Query. No N+1 problem to solve in a single-user app. |
| RPC over JSON-RPC | Skip | Loses Swagger UI and HTTP semantics (caching, statuses) for no win. |

Confidence: HIGH.

## Auth (Deferred — Plan So v1 Doesn't Box Itself In)

**v1:** No auth. All routes accessible. Trust boundary = Tailscale/LAN.

**v1.5 shape (only if hosting changes):**
1. Single passphrase env var (`APP_PASSPHRASE`).
2. Login route issues a signed httpOnly cookie (`itsdangerous` or `authlib`'s session signer).
3. `Depends(require_session)` on the FastAPI router.
4. No password reset, no MFA, no OAuth — single user means: lose the passphrase, edit the env, restart.

**What v1 must not do** to keep this door open:
- Don't bind logic to "current user" anywhere — there is no user concept.
- Don't add per-row `user_id` columns — single tenant.
- Do put all routes under one router so adding a single `Depends` is a one-liner later.

**What NOT to introduce in v1.5:** Auth0, Supabase Auth, Clerk, NextAuth/Auth.js — all of them violate the "no SaaS / single-compose" constraint or pull in a Next.js/JS-only auth pattern. A 60-line cookie-session module is right-sized.

Confidence: HIGH on shape, MEDIUM on exact lib (could swap `itsdangerous` for `starlette.middleware.sessions`).

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|-------------|-------------|-------------------------|
| FastAPI | **Litestar 2.21** | If you become serialization-bound (you won't on a single-user app) or want msgspec instead of Pydantic. Smaller community → harder when you hit a corner. |
| FastAPI | **Django 5 + DRF** | If you find yourself wanting an admin UI for free; cost is async story is weaker and you carry the whole framework for one user. |
| FastAPI | **Flask 3** | If async genuinely doesn't buy you anything and you prefer sync; loses OpenAPI auto-gen and modern type story. |
| Postgres | SQLite + WAL | Pi Zero / 256 MB device, or you hate running a DB container. Use Alembic batch mode. |
| APScheduler | systemd timer + CLI script | If you want the poller to survive an app crash without restart logic; loses shared state. |
| APScheduler | Arq + Redis | Only if you later need fan-out to multiple poll workers (you won't, single token = single worker). |
| psycopg 3 | asyncpg | Slightly faster, but SQLAlchemy 2 with psycopg3 is the path with the most examples; asyncpg is a fine swap if perf becomes an issue. |
| Decimal + custom `Money` | `py-moneyed` | If a future contributor demands i18n-formatted currency rendering and you're tired of writing it yourself. Stale package, low priority. |
| React | **SvelteKit 2 + Svelte 5** | If bundle size really matters (it doesn't on LAN) or you want SSR; smaller chart ecosystem (LayerChart vs Recharts). |
| TanStack Query | SWR 2 | Simpler API; equally good for this scale. Pick TanStack only because it pairs better with React Router 7 loaders. |
| Recharts | ECharts | Multi-axis financial charts (candlesticks, regulatory dashboards). Overkill here. |
| Tailwind 4 | Vanilla CSS / CSS Modules | Tiny project where you want zero build-time CSS magic. You'll outgrow it by feature 3. |
| shadcn/ui | **Mantine 7** | Want everything pre-styled, willing to accept a runtime dep + upgrade churn. |
| OpenAPI codegen | Hand-rolled fetch + Zod schemas | Tiny API surface (<10 endpoints). Fine for a 3-day prototype, painful by month 2. |
| pgvector (later) | sqlite-vec / chromadb | Only if you went SQLite. With Postgres, pgvector is the answer. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|-------------|
| `requests` (sync) for the Mono client | Blocks the event loop or forces threadpool kludges; loses native timeout semantics. | `httpx.AsyncClient` |
| `psycopg2` / `psycopg2-binary` | v3 is the actively developed line, async-native, better typing. | `psycopg[binary,pool]` 3.x |
| `py-moneyed` | Last release 2022; minimal value over a 30-line `Money` dataclass. | Hand-rolled `Money(Decimal, currency)` |
| **Float for money** anywhere — DB, Pydantic model, JSON. | `0.1 + 0.2 != 0.3`. End of argument. | `Decimal` + `NUMERIC(20,4)` + string-encoded JSON |
| Celery / RabbitMQ / Redis broker | Adds 2 containers + ops surface for a 1-job scheduler. Violates "single compose up". | APScheduler in-process |
| Kafka / event-sourcing | Enterprise pattern; one user, one app, one DB. | Plain SQL writes |
| Kubernetes | Single-node homelab; k8s is a different planet. | Docker Compose |
| Auth0 / Clerk / Supabase Auth | SaaS dependency; violates privacy constraint and single-compose constraint. | Cookie + passphrase if/when needed |
| Hasura / PostgREST | Auto-generated CRUD APIs that bypass your domain rules (reconciliation, transfer detection, FX rollups) — exactly the rules you need to *enforce*. | FastAPI handlers |
| Django + DRF | Heavy ORM-first framework; you won't use 60% of it (admin, sessions, contrib auth) and async story is weaker than FastAPI. | FastAPI |
| Next.js / SSR | No SEO need; LAN-only. SSR adds Node runtime in production for no user benefit. | Vite SPA |
| `forwardRef`-based component libs that don't support React 19 | React 19 deprecates `forwardRef` in favor of `ref` as a prop. | shadcn (post-codemod) / Mantine 7+ |
| Material UI v5 | Big runtime, opinionated theming that fights Tailwind. | shadcn/ui |
| Chart.js's React wrapper for v1 | Imperative under the hood, awkward responsive containers. | Recharts |
| `moment.js` | Maintenance mode, large bundle. | `date-fns` |
| Heavy state libs (Redux, MobX) | Single-user JSON dashboard. | TanStack Query + `useState` |
| `pip` + `requirements.txt` + `venv` by hand | uv replaces all of this with one binary, faster and reproducibly. | `uv` |
| `black` + `isort` + `flake8` separately | Ruff replaces all three (and 100 plugins). | `ruff check && ruff format` |
| `mypy --strict` *only* | Pyright/basedpyright catches more in async code. mypy is still fine; either is acceptable. | basedpyright (or mypy 2.0 + strict) |

## Stack Patterns by Variant

**If you decide v1 must run on a Raspberry Pi Zero / 512 MB device:**
- Swap Postgres → SQLite (WAL, busy_timeout=5000).
- Use Alembic with `--render-as-batch` for ALTERs.
- Keep everything else identical. Plan a Postgres migration as v1.5 if pgvector becomes interesting.

**If user changes mind and accepts SaaS for "just one thing":**
- Don't. The privacy constraint is the *reason* this project exists. Reject the temptation.

**If LLM categorizer ships earlier than v1.5:**
- Local: Ollama in another compose service, called via httpx from the categorizer module. No code change in the rest of the stack.
- API: Anthropic / OpenAI SDK called from a `Categorizer` interface. The interface (`def classify(tx: Transaction) -> Category`) is the *only* thing that needs to exist in v1.

**If user adds PrivatBank / Wise later:**
- Add an `ImporterProtocol` with `pull(since: datetime) -> list[RawTxn]`. Mono importer implements it. New importers slot in. No DB change beyond `account.source` already being there.

## Version Compatibility Notes

| Package A | Compatible With | Notes |
|-----------|-----------------|-------|
| FastAPI 0.136 | Pydantic 2.13, Starlette 0.41+ | Pin both to avoid surprise minor-version churn between Starlette and FastAPI. |
| SQLAlchemy 2.0.49 | Alembic 1.18.4 | Current stable pair. |
| SQLAlchemy 2.0 + psycopg 3 | Use URL `postgresql+psycopg://` | Not `postgresql+psycopg2://`. Common mistake. |
| Tailwind CSS 4 | Vite 8 + `@tailwindcss/vite` plugin | v4 is *not* drop-in compatible with v3 configs; new project = no problem. |
| React 19 | shadcn/ui CLI 3+ | Older shadcn used `forwardRef`; CLI 3+ ships ref-as-prop primitives. Use `npx shadcn@latest`. |
| TanStack Query 5 | React 19 | Native support; no peer-dep workaround needed. |
| `psycopg[pool]` 3.3 | Postgres 17 | Driver works against any modern PG; `pool` extra is the connection pool. |
| Python 3.13 | `holidays` 0.x | Works fine on 3.13. 3.14 may need a holidays bump — stay on 3.13 for now. |
