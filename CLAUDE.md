## Project

**finance-bro**

A self-hosted personal-finance tool for one person. It pulls transactions from Monobank, categorizes them automatically, reconciles duplicates and internal transfers, and shows where the money actually goes — all on hardware the user controls. Built for someone who is frustrated with existing budgeting tools that demand manual upkeep and won't host their financial data on third-party clouds.

**Core Value:** **Automatic visibility into where my money goes — zero manual upkeep, on hardware I own.**

Every prioritization tradeoff resolves toward: less manual work for the user, and more privacy. Features that demand ongoing tagging, that ship data to third parties, or that move attention away from the spending picture lose.

### Constraints

- **Privacy**: No third-party cloud services for primary data storage or processing. All transaction data lives on user-controlled hardware. — Privacy is a stated motivation; violating this defeats the purpose of building it.
- **Tech stack**: Python backend, JS frontend. — User preference; favors Python's LLM tooling ecosystem for the eventual hybrid-categorizer work.
- **Deployment**: Docker on homelab/NAS. Single `docker compose up` style deploy. — Target environment is a home server, not a managed cloud.
- **External API**: Monobank personal API, 1 request per 60 seconds per token. — Hard rate limit; informs poll cadence and backfill strategy.
- **Single-user**: No multi-tenancy. — Stated requirement; building it in is wasted complexity.
- **Network-gated**: No app-level auth in v1. — Tailscale/LAN handles access control; revisit only if exposure model changes.
- **Time horizon**: Solid MVP, ~1–2 months of evening work. — User's stated capacity; rules out long-tail polish for v1.
- **Scope discipline**: Visibility, not planning. — Core Value rules out budgets/forecasts/alerts in v1 even when "while we're at it" tempting.

## Database Decision: Postgres > SQLite (for *this* project)
| Criterion | SQLite | Postgres | Verdict |
|-----------|--------|----------|---------|
| Single-user fit | Built for it | Overkill in theory | SQLite wins on paper |
| ACID for money | Yes | Yes | Tie |
| Decimal/numeric arithmetic | `REAL`/`NUMERIC` is stored as text — fine, but no native arithmetic precision guarantees | First-class `NUMERIC(20,4)` with exact arithmetic in SQL | **Postgres** — money rollups happen in SQL aggregations |
| Concurrent read while writing | WAL mode allows it, but writers serialize globally | MVCC, no global writer lock | **Postgres** — poller + UI both happily writing/reading |
| Joins against FX rate table | Fine for small data | Fine, with proper plans | Tie |
| Backup story | `sqlite3 .backup` file copy — trivial | `pg_dump | gzip` — also trivial | Tie (both 1-line cron) |
| Migrations | Alembic supports both, but SQLite ALTER TABLE is anemic — most schema changes require batch operations / table rebuilds | Full ALTER TABLE, types, constraints | **Postgres** — finance schemas evolve a lot |
| Compose footprint | Zero | One container, ~80 MB RAM idle | SQLite wins on resource use |
| LLM categorizer extension | `pgvector` exists for Postgres, no equivalent for SQLite | Drop-in `pgvector` extension | **Postgres** — keeps the LLM door open |
| Future "I want to query from another tool" | File lock contention | Connection-based | **Postgres** |
## Money / Decimal Handling
# domain/money.py
- `transactions.amount` — `NUMERIC(20, 4)` not null
- `transactions.currency` — `CHAR(3)` not null
- Mono returns minor-unit integers (kopecks/cents). Convert at the edge: `Decimal(minor) / Decimal(100)` (or `1000` for some currencies — UAH/USD/EUR are all 2-place).
- All UAH-rollup math in SQL using `NUMERIC` ops; `transactions JOIN fx_rates ON tx.date = fx.date AND tx.currency = fx.currency`.
- Never `float()` a `Decimal` on the way out except for the final JSON serialization, and even then prefer string transport (`Decimal -> str`) so the JS side doesn't reintroduce float drift. The `tan-stack/react-query` hook can `Number()` only at the chart boundary.

## Mono Polling Strategy (1 req / 60 s constraint)
- `/personal/statement/{account}/{from}/{to}` — **1 call per 60 s per token**.
- Maximum window per call: **31 days + 1 hour (2,682,000 s)**.
- `/personal/client-info` — same 60s cooldown applies; calling either resets the timer for both.
- Celery + Redis broker: enormous overkill — 2 extra containers, broker ops, serialization, etc. — for 1 task every 65 s.
- Arq: Redis-based; same overhead.
- Dramatiq: ditto.
- systemd timer / host cron calling a CLI: works, but you lose shared state (last-fetched cursor, in-memory backoff) and your "single docker compose up" story now requires host-side cron files.
- Plain `asyncio.create_task` in a loop: works, but you lose APScheduler's misfire/coalesce semantics for free, which matter when the NAS sleeps or restarts.
## Frontend Decision
### Why React + Vite (not SvelteKit, not HTMX)
| Option | Verdict | Reasoning |
|--------|---------|-----------|
| **React 19 + Vite + TS** ✅ | Pick | Largest pool of charts, components, hooks, AI assistance. The user already prefers JS — the gain from Svelte/Vue isn't worth the smaller chart/component ecosystem. |
| SvelteKit 2 + Svelte 5 | Reasonable alt | Smaller bundle, runes are nice, but Recharts-equivalent (LayerChart) is less mature, and the user-prefers-JS constraint already accepts framework overhead. |
| Vue 3 | Fine but worse fit | Smaller English-language solo-dev community than React; no objective edge here. |
| **HTMX + Jinja** | Skip for this project | HTMX is genuinely good for forms-and-CRUD, but the Spending Dashboard is interactive (filter, drill-down by category, time range, comparison vs prior month). Building that with HTMX means lots of partial templates and `hx-get` handlers; the JS state model wins for this UX. The user explicitly prefers JS — only override if HTMX gave a 2-week delivery edge, and for this UX it doesn't. |
### Why TanStack Query + nothing else
- **Server state** (transactions list, accounts, categories, FX rates) → TanStack Query 5. Caching, revalidation, mutations, optimistic updates.
- **URL state** (current filter, selected month) → React Router 7's loaders/`useSearchParams`.
- **Truly local UI state** (modal open, form input) → `useState`.
### Why Recharts (not Chart.js / ECharts / uPlot / Plotly)
| Library | Verdict | Why |
|---------|---------|-----|
| **Recharts 3** ✅ | Pick | Declarative React API matches the rest of the codebase; defaults look fine; ~50 KB gz; easy responsive containers; pie/bar/line/area covers every chart in the dashboard. |
| ECharts 6 | Overkill | Most powerful, ugliest defaults, biggest bundle (~900 KB), tons of imperative config. Right for enterprise BI, wrong for a personal dashboard. |
| Chart.js 4 | Reasonable alt | Smaller than ECharts, but imperative + canvas-only. React wrapper is community-maintained. |
| Plotly | Skip | Heavyweight scientific charts. |
| uPlot | Skip | Best-in-class for huge time series; you have at most a few thousand transactions a month — uPlot's value (10× faster on 1M points) doesn't apply. |
### Why Tailwind 4 + shadcn/ui
- Tailwind 4 ships its own Vite plugin (`@tailwindcss/vite`) and replaces the JS config with CSS-native `@theme {}` blocks. Less to configure than v3.
- shadcn/ui is **not a dependency** — `npx shadcn@latest add button dialog input ...` copies Radix-based components into `src/components/ui/` that you own and can mutate. This avoids the lock-in problem with Mantine / Park UI / Chakra: when the vendor pivots, you don't have to rewrite. shadcn explicitly supports Tailwind v4 + React 19 since CLI v3.
- Mantine is a fine alternative if you want everything pre-built, but you trade ownership for upgrade pain and ~150 KB of CSS-in-JS runtime.

## Stack Patterns by Variant
- Swap Postgres → SQLite (WAL, busy_timeout=5000).
- Use Alembic with `--render-as-batch` for ALTERs.
- Keep everything else identical. Plan a Postgres migration as v1.5 if pgvector becomes interesting.
- Don't. The privacy constraint is the *reason* this project exists. Reject the temptation.
- Local: Ollama in another compose service, called via httpx from the categorizer module. No code change in the rest of the stack.
- API: Anthropic / OpenAI SDK called from a `Categorizer` interface. The interface (`def classify(tx: Transaction) -> Category`) is the *only* thing that needs to exist in v1.
- Add an `ImporterProtocol` with `pull(since: datetime) -> list[RawTxn]`. Mono importer implements it. New importers slot in. No DB change beyond `account.source` already being there.
